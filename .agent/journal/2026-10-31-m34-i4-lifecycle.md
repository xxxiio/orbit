# Journal Entry: 2026-10-31 — M34 I4 automatic lifecycle accepted

## Context

A backup capability is only protective if it runs without being remembered and if
upgrades cannot replace binaries on an unprotected workspace. I4 added the optional
automatic schedule, retention and the complete `orbit update` pre-upgrade recovery
point, all reusing the shared service. Acceptance is recorded on the frozen tree.

## Work completed

- `.agent/tasks/TASK-0019.md` moved to `completed`: all acceptance criteria checked
  with I4 evidence.
- Automatic lifecycle: `crates/orbit-server/src/main.rs` now spawns
  `backup_scheduler`. It re-reads `<ORBIT_BACKUP_DIR>/policy.json` every 15 minutes
  (first check about 30 seconds after startup), creates a verified
  `orbit-<stamp>-automatic-<schedule>.orbitbak` when a `daily`/`weekly` policy is
  due, avoids duplicating a daily backup within the same UTC day, and applies
  retention while protecting the new archive. `disabled`/`before-upgrade` never run
  on a timer; a policy change through the CLI or Web GUI takes effect without a
  restart.
- Retention: `max_retained`, `min_retention_days` and optional `max_total_bytes`;
  cleanup only after a verified creation, never removing the last verified
  recovery point or user-managed external copies.
- `orbit update`: creates a complete, verified recovery point (database + vault +
  attachments + normalized config; label `before-update-<from>-to-<to>`), inspects
  and deep-verifies it after publish, fails closed with "refusing to update" and
  replaces no binaries when it cannot (missing attachment object / non-Orbit DB),
  applies retention after verification while protecting the new archive, and keeps
  `--check` read-only.
- EC-010 and EC-011 were checked in MILESTONE-0034 and the roadmap with evidence.

## Decisions made

- Automatic backups run in the long-running server process; a local-only CLI
  installation has no background scheduler and uses manual/timer backups. This is
  documented rather than pretending the CLI is always scheduled.
- Cleanup is gated on a verified creation and always protects the newest verified
  recovery point; the scheduler also fails closed on an incomplete workspace
  instead of publishing an incomplete archive.
- The pre-upgrade recovery point is a hard gate on `orbit update`; an update that
  cannot verify a complete workspace recovery point must not replace binaries.
