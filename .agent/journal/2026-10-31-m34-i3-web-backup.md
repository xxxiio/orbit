# Journal Entry: 2026-10-31 — M34 I3 Web backup management accepted

## Context

I1/I2 gave the CLI a complete backup/restore path. I3 put that same capability in
the reference web product: a server transport over the shared `orbit-backup`
service plus a Backup & Restore settings page, with the destructive replacement
path kept out of the browser. Acceptance is recorded on the frozen tree.

## Work completed

- `.agent/tasks/TASK-0018.md` moved to `completed`: all acceptance criteria checked
  with I3 evidence.
- Server routes: `GET/POST /v1/backups`, `GET /v1/backups/{id}`,
  `POST /v1/backups/{id}/verify`, `GET /v1/backups/{id}/download`,
  `GET/PUT /v1/backups/schedule`, `POST /v1/restores/preflight`,
  `POST /v1/restores/isolated`, `POST /v1/restores/replace-plan`. Product responses
  are path-free; backups are addressed by id resolved inside `ORBIT_BACKUP_DIR`;
  isolated targets are generated under `ORBIT_BACKUP_RESTORE_ROOT`; downloads are
  memory-buffered and capped by `ORBIT_BACKUP_DOWNLOAD_MAX_BYTES` (default 512 MiB,
  `413` above it).
- Web page `/settings/backup` (sidebar footer + command palette): Last verified
  backup, Server backup folder (Writable/Not writable), Automatic backups policy
  editor, Create a backup, Backup history (Inspect/Verify/Download), Backup details
  drawer, and a Restore panel with Isolated copy (typed `RESTORE`) versus Replace
  authority (administrator key; only writes the offline maintenance plan
  `<db>.restore-pending.json`).
- Authorization keeps product principals on list/create/inspect/verify/download/
  schedule/isolated restore; only the replacement plan requires the administrator
  credential (local-trusted without an admin bearer gets `403`).
- EC-009 was checked in MILESTONE-0034 and the roadmap with evidence.

## Decisions made

- The browser never accepts a server filesystem path and never replaces the live
  database; recovery that changes the authority is an explicit offline maintenance
  action.
- The server is a transport over the shared service, not a second archive
  implementation, so CLI and Web GUI cannot drift.
- Archive downloads are buffered and capped in this offline build (documented
  limitation, TODO-0020) rather than adding a streaming dependency.

- Very large archive downloads cannot be completed in the browser under the
  in-memory cap; documented, large archives are copied from the server folder.
