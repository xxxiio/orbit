# Task: I1 — Backup core: shared Rust service, `.orbitbak` format and fenced create/verify

## Objective

Orbit can create and inspect a complete, consistent, portable `.orbitbak` workspace
archive from the CLI through one shared Rust service, and can verify it in full
before relying on it.

## Specification

- Inputs: an Orbit workspace with an authoritative SQLite database (WAL mode
  possible), a Markdown vault, attachment objects and normalized configuration.
- Output: a versioned `.orbitbak` archive containing the SQLite snapshot, vault,
  referenced attachment objects, normalized non-secret configuration and a manifest
  with relative file paths, sizes, SHA-256 hashes, total size and a component
  inventory.
- The SQLite snapshot uses SQLite's supported online backup API, not a copy of the
  live main file.
- A bounded writer fence makes the database, vault and attachment references
  correspond to one snapshot instant.
- Creation is failure-safe: write to staging, verify before publish, publish
  atomically, clean temporary files, return a nonzero and clear error on failure,
  and never mutate the original workspace.
- Archive paths are relative only; absolute paths and `..` traversal are rejected.
- Format versions are explicit; a newer format is rejected with an actionable
  message.
- Normalized configuration excludes secrets by an explicit allow-list.
- CLI: `orbit backup create|list|inspect|verify`, with default and external
  archive directories.
- Failure cases: interrupted creation, disk-full, permission failure, missing
  vault/attachment file, corrupt manifest and unsupported format version.

## Ordered plan

1. Define the `.orbitbak` v1 archive layout, manifest fields and component
   inventory; document relative-path and format-version rules.
2. Create the shared backup crate with the archive model, manifest writer/reader
   and typed errors.
3. Implement the consistent snapshot: start the SQLite online backup with a
   bounded writer fence, collect vault and attachment references inside the
   window, then release the fence.
4. Implement failure-safe creation: staging directory, verification, atomic
   publish, cleanup and nonzero error reporting.
5. Implement `inspect` and `verify`: manifest completeness, per-file hashes,
   SQLite integrity, schema compatibility, attachment presence and vault manifest
   consistency.
6. Wire `orbit backup create|list|inspect|verify` to the service.
7. Add unit and integration tests against a disposable workspace, including the
   WAL, interrupted-create and newer-format cases.
8. Record evidence in this task and the milestone EC rows; update the acceptance
   and evidence records when I1 is accepted.

## Acceptance criteria

- [x] AC-001: `orbit backup create` writes a versioned `.orbitbak` with the SQLite
  snapshot, Markdown vault, referenced attachment objects, normalized non-secret
  configuration and a manifest with relative paths, sizes, per-file SHA-256, total
  size and component inventory.
- [x] AC-002: The SQLite snapshot uses the supported online backup API and a
  bounded writer fence, so database, vault and attachment references match one
  snapshot instant; a WAL-mode workspace is handled without copying the live main
  file.
- [x] AC-003: Creation stages, verifies before publish and publishes atomically;
  interrupted or failed creation leaves no partial published archive, returns a
  clear nonzero error, cleans temporary state and never mutates the workspace.
- [x] AC-004: `orbit backup list` and `orbit backup inspect` report archives from
  the default and an external directory with format version, schema version,
  component inventory and manifest summary.
- [x] AC-005: `orbit backup verify` checks archive structure, manifest
  completeness, per-file hashes, SQLite integrity, schema compatibility,
  referenced attachment presence and vault manifest consistency, and exits nonzero
  on any failure.
- [x] AC-006: The reader rejects absolute or parent-traversal paths and newer
  format versions with actionable messages; secret configuration keys are absent
  from the archive by the documented allow-list.
- [x] AC-007: New backup unit, integration and failure tests pass and the affected
  workspace gates pass; the exact commands and archive fixture are recorded as
  evidence.
- [x] AC-008: The backup format is documented with container, layout, manifest
  fields, version compatibility, relative-path rules, traversal rejection, secret
  exclusions, verification semantics and the verification sidecar.

## Validation evidence

- `cargo test -p orbit-backup --offline`: **126 passed / 0 failed across 12 test
  targets**. The I1 backup-core targets are 49 lib tests (format, tar, manifest,
  snapshot, writer fence and policy), `create_verify` 14, `verify_integrity` 9 and
  `inspect_list` 9 (81 backup-core tests); the remaining targets exercise
  restore/retention/policy work completed by I2/I4 and are not claimed as I1
  evidence.
- `cargo test --workspace --locked --offline`: 2032 passed, 0 failed.
- `cargo check -p orbit-cli --offline`: passed. `cargo build --offline -p
  orbit-cli`: passed. `cargo fmt --all -- --check` and `cargo clippy --workspace
  --all-targets --locked --offline -- -D warnings`: clean.
- CLI end-to-end, run with a temporary `HOME` and a disposable database (the
  repository workspace was not touched):
  - `orbit backup create` with the default directory, `--output`, `--label` and
    `--json` produced a verified `.orbitbak` plus `<archive>.verify.json`.
  - `orbit backup list` worked on the default and an external directory; a copied
    archive reported `unknown`, a corrupt archive was skipped, and non-`.orbitbak`
    files were ignored.
  - `orbit backup inspect` showed manifest, totals, counts, inventory and the
    creation verification.
  - `orbit backup verify` passed the deep 8/8 checks (structure, manifest, paths,
    `file_hashes`, `sqlite_integrity` with 59 tables, `schema_compatibility`,
    `attachment_presence`, `vault_consistency`); `--structural-only` behaved as
    documented.
  - A tampered archive exited `1`; a permission-denied destination (directory
    mode `0500`) exited `4`, left the directory mode unchanged and did not publish
    an archive.
- Independent Lead smoke test: `create` succeeded over a live `orbit-server`
  (WAL with an active connection; the fence was released and the server stayed
  healthy), a project created through the server API appeared in the restored
  copy, an isolated restore opened with matching tasks, notes and attachment
  content (exported attachment SHA-256 matched), and replace-with-confirm preserved
  the previous workspace plus the recovery journal.
- Verification semantics verified: `verify_archive` returns `Ok` with
  `report.ok == false` for content, manifest, hash, SQLite and schema failures
  (including bad magic and truncation); it returns `Err` only when the file cannot
  be opened. `file_hashes` is reported `skipped`, not `pass`, when structure fails
  first.
- Format documentation: `docs/reference/backup-format.md` documents the ustar
  container, archive layout, manifest fields, version compatibility, relative-path
  rules, traversal rejection, default secret exclusion, verification semantics and
  the verification sidecar (EC-008).
- Resolved defect: `util::create_private_dir` used to chmod an existing destination
  directory (`0500` → `0700`) and let a denied backup succeed. It now tightens
  permissions only when it creates the directory. Regression test:
  `existing_directory_permissions_are_never_rewritten`. The permission-denied
  destination run above is the end-to-end check.
