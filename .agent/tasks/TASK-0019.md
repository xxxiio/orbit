# Task: I4 — Automatic backups and lifecycle: schedules, retention and pre-upgrade recovery point

## Objective

Orbit can protect itself on a schedule and before upgrades: optional automatic
backups run in the configured mode, retention removes only redundant verified
archives, and `orbit update` refuses to proceed without a complete pre-upgrade
recovery point when a workspace is present.

## Specification

- Automatic backup modes: disabled (default), daily, weekly and pre-upgrade.
- Configuration covers destination, mode/schedule and retention: max retained
  count, minimum retention period and optional maximum storage.
- Cleanup runs only after a verified creation, never removes the last verified
  recovery point and never removes the user's external copies.
- Backups on the same disk are not protection against disk failure; the
  documentation and UI say so.
- A pre-upgrade recovery point is a complete workspace backup, not a database-only
  copy.
- If a complete pre-upgrade recovery point cannot be created, `orbit update` fails
  closed and does not upgrade.
- Failure cases: destination full, verification failure during a scheduled run,
  retention policy that would remove the last verified point, and update with a
  workspace but no writable destination.

## Ordered plan

1. Define and parse the backup configuration (mode, destination, retention policy)
   with startup validation and documented defaults.
2. Implement the scheduler for daily/weekly/pre-upgrade modes and the
   disabled-by-default behaviour.
3. Implement retention evaluation and cleanup that runs only after a verified
   creation and protects the floor.
4. Integrate the complete pre-upgrade recovery point into `orbit update`.
5. Add unit and integration tests, including failure injection for full disk and
   fail-closed update.
6. Record evidence for EC-010 and EC-011; update configuration documentation.

## Acceptance criteria

- [x] AC-001: Backup mode and schedule configuration (disabled/daily/weekly/
  before-upgrade) are parsed, validated and documented with a safe default.
- [x] AC-002: Retention honours max retained, minimum retention period and optional
  max storage; cleanup runs only after a verified creation and never removes the
  last verified recovery point or external copies.
- [x] AC-003: `orbit update` creates a complete workspace recovery point (not
  database-only) when a workspace is present and fails closed without upgrading
  when it cannot.
- [x] AC-004: Failure cases (full destination, verification failure, unsafe
  retention, unwritable destination) are refused with clear errors and leave the
  workspace recoverable.
- [x] AC-005: The affected Rust gates pass and the exact commands and configuration
  fixtures are recorded as evidence.

## Validation evidence

- Scheduler (wired into `crates/orbit-server/src/main.rs`): a server started with
  `ORBIT_BACKUP_DIR` containing `policy.json` `{version:1, schedule:"daily"}`
  created a verified `orbit-<stamp>-automatic-daily.orbitbak` about 30 seconds
  after startup; a second tick on the same UTC day created no duplicate; the
  archive verified 8/8; the scheduler re-reads `policy.json` every 15 minutes, so
  policy changes take effect without a restart. A workspace with missing
  attachment objects made the automatic backup fail closed (no incomplete archive
  published) and the live workspace stayed healthy.
- Retention: `orbit backup schedule set/show` and `orbit backup retention apply
  [--dry-run]` work; cleanup runs only after a verified creation, protects the last
  verified recovery point and never touches external copies (`policy` 7 and
  `retention` 8 tests plus CLI acceptance).
- `orbit update`: creates a complete verified workspace recovery point
  (database + vault + attachments + normalized config, label
  `before-update-<from>-to-<to>`), inspects and deep-verifies it after publish,
  fails closed with "refusing to update" and replaces no binaries when it cannot
  (missing attachment object / non-Orbit DB), applies retention after verification
  while protecting the new archive, and `--check` remains read-only.
  Evidence is helper-level: the full `orbit update` network flow was not run
  offline in this acceptance.
- `cargo test -p orbit-backup --offline`: 126 passed / 12 targets;
  `cargo test --workspace --locked --offline`: 2032 passed, 0 failed; fmt and
  clippy `-D warnings` clean.
- CLI failure-injection matrix (`web/evidence/m34-recovery/failure-injection.json`):
  schedule/retention protecting the last verified point, interrupted backup
  (SIGKILL: no partial archive or staging, workspace intact), corrupted/truncated
  archive, unsupported format v999 rejected with the upgrade message, and
  permission-denied destinations all behaved as specified.

## Outcome

Completed. The automatic lifecycle is implemented and verified: the long-running
server schedules daily/weekly backups from a shared `policy.json`, does not
duplicate a daily backup within a UTC day, fails closed on an incomplete workspace,
and applies retention only after a verified creation while protecting both the new
archive and the last verified recovery point. `orbit update` is now data-safe: it
creates and verifies a complete workspace recovery point before replacing binaries
and refuses to upgrade when it cannot. EC-010 and EC-011 pass with the documented
limitation that the full update network flow is helper-level evidence only.
