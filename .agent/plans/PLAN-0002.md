# Execution Plan

## Outcome

MILESTONE-0034 — Orbit can create a complete, consistent, portable, verifiable
`.orbitbak` workspace backup and restore it safely through the CLI and the Web GUI,
backed by one shared Rust service, so that Orbit can become the source of truth for
its own development including MCP and Herdr agent work.

## Why planning is required

The outcome spans a versioned archive format, a consistent snapshot across three
different stores, a destructive and security-sensitive restore path, server API
and browser surfaces, automatic lifecycle management, integration with `orbit
update`, and failure/rehearsal proof. Each part depends on the previous one and none
can be honestly completed and accepted in one deterministic step.

## Preconditions

- MILESTONE-0033 is complete and the corrected web UX was accepted by the project
  maintainer on 2026-10-31 for internal dogfooding.
- The roadmap, current task, current next step, change impact, acceptance and
  evidence records are switched to M34 before implementation.
- The existing authoritative SQLite store, Markdown vault, attachment object store
  and normalized configuration are identifiable and readable.
- The existing server authorization architecture, CLI, web client and `orbit
  update` command are available.
- A disposable workspace fixture can be created from test data.

## Assumptions and unknowns

- Assumption: the bundled SQLite build exposes the supported online backup API; if
  not, the slice stops rather than copying a live main file.
- Assumption: referenced attachment objects can be enumerated from authoritative
  records without scanning unrelated files.
- Assumption: normalized configuration can be rebuilt from an explicit non-secret
  allow-list rather than copying raw config.
- Assumption: the Web GUI can add a settings section without changing the existing
  authentication architecture.
- Unknown: the exact attachment-store abstraction and whether any objects are
  referenced only by connected clients.
- Unknown: the current `orbit update` hook shape for a pre-upgrade recovery point.
- Unknown: how connected-client outbox and staged uploads are detected for the
  fail-closed restore rule.

## Slices

### SLICE-001 — I1 backup core: shared Rust service, `.orbitbak` format, fenced create/verify

- **Status:** completed
- **Depends on:** none
- **Advances exit criteria:** EC-001, EC-002, EC-003, EC-004
- **Validation tier:** 3

#### Scope

- Versioned `.orbitbak` v1 layout, manifest model and component inventory.
- Shared backup crate and `BackupService` with create/list/inspect/verify.
- SQLite online-backup snapshot with a bounded writer fence and WAL handling.
- Failure-safe staging, verify-before-publish, atomic publish and cleanup.
- CLI `orbit backup create|list|inspect|verify` on default and external
  directories.

#### Must not change

- The authoritative database schema and existing record semantics.
- The Markdown vault format or attachment addressing.
- Existing CLI commands outside the new `orbit backup` family.
- Any live workspace file of the source workspace during creation.

#### Acceptance criteria

- [x] SC-001: A produced `.orbitbak` contains the SQLite snapshot, vault,
  referenced attachments, normalized non-secret config and a complete manifest
  with relative paths, sizes, SHA-256, total size and component inventory.
- [x] SC-002: The snapshot uses the online backup API and a bounded writer fence;
  a WAL-mode workspace is handled without copying a live main file.
- [x] SC-003: Creation stages, verifies, publishes atomically and cleans up;
  interrupted creation is nonzero and leaves no partial published archive or
  workspace mutation.
- [x] SC-004: `list`, `inspect` and `verify` work on default and external
  directories; `verify` checks structure, manifest, hashes, SQLite integrity,
  schema compatibility, attachment presence and vault manifest consistency and
  exits nonzero on failure.
- [x] SC-005: Absolute and parent-traversal paths and newer format versions are
  rejected with actionable errors, and secret configuration is excluded.

### SLICE-002 — I2 restore engine: preflight, isolated restore, maintenance replacement and rollback

- **Status:** completed
- **Depends on:** SLICE-001
- **Advances exit criteria:** EC-005, EC-006, EC-007
- **Validation tier:** 4

#### Scope

- `restore --dry-run` preflight report with no mutation.
- Isolated restore into a new location that opens as a working Orbit instance.
- Maintenance replacement with explicit authorization, maintenance boundary,
  staged verification, switch and rollback preservation.
- Connected-replica fail-closed detection and reconciliation warning.
- CLI `orbit backup restore`.

#### Must not change

- The active workspace during isolated restore.
- A live active-server database during replacement.
- Existing backup archives produced by SLICE-001.
- Existing server authorization semantics for administrative operations.

#### Acceptance criteria

- [x] SC-006: `restore --dry-run` reports target, source, schema compatibility,
  objects replaced, preservation plan, downtime, connected warnings and
  non-restorable dependencies, and mutates nothing.
- [x] SC-007: An isolated restore verifies and opens successfully as a working
  Orbit instance without overwriting the active workspace.
- [x] SC-008: Replacement requires explicit authorization and a maintenance
  boundary, stages and verifies before switching, and preserves the previous
  workspace for rollback.
- [x] SC-009: Restore while the target is active, a wrong destination, an
  incompatible schema and an incompatible connected replica all fail closed with
  recovery of the original workspace.

### SLICE-004 — I4 automatic backups and lifecycle: schedules, retention and pre-upgrade recovery point

- **Status:** completed
- **Depends on:** SLICE-001, SLICE-002
- **Advances exit criteria:** EC-010, EC-011
- **Validation tier:** 4

#### Scope

- Backup configuration: mode (disabled/daily/weekly/pre-upgrade), destination,
  retention (max retained, minimum retention period, optional max storage).
- Scheduler and safe default behaviour.
- Retention cleanup that runs only after a verified creation and protects the
  last verified recovery point and external copies.
- Complete pre-upgrade recovery point in `orbit update`, failing closed when it
  cannot be created.

#### Must not change

- The default behaviour of `orbit update` for users without a workspace.
- Existing archive semantics or verification rules.
- User-managed external archive copies.
- Existing configuration files for unrelated settings.

#### Acceptance criteria

- [x] SC-014: Configuration parses and validates all modes and retention limits
  with a documented safe default.
- [x] SC-015: Retention cleanup runs only after a verified creation, never removes
  the last verified recovery point and never removes external copies.
- [x] SC-016: `orbit update` creates a complete workspace recovery point when a
  workspace is present and fails closed without upgrading when it cannot.

## Risks and stop conditions

- Stop if the SQLite build cannot provide the supported online backup API; do not
  fall back to copying a live database file.
- Stop and re-plan if the vault or attachment layout cannot be enumerated inside a
  bounded writer fence without changing authoritative storage semantics.
- Stop if a restore design requires overwriting a live active-server database; the
  maintenance boundary is non-negotiable.
- Stop if normalized configuration cannot exclude secrets by an explicit
  allow-list without changing user-visible configuration behaviour.
- Stop if the rehearsal or failure-injection evidence cannot be produced honestly;
  leave the criterion unmet rather than waiving it silently.
- Connected-client outbox/staged-upload coverage is a documented server-backup
  limitation, not a hidden guarantee; any conflicting requirement returns to
  planning.
